## P1 — Data + API
- [H3] db — server talks to Postgres directly (`postgres` v4, server-only `DATABASE_URL`), not via supabase-js: ingest must hold ONE transaction across `FOR UPDATE` + TypeScript `assess()`, which PostgREST cannot do. supabase-js stays for Auth + Realtime. Writes bypass RLS on purpose; every write is a zod-validated route handler.
- [H3] db — ingest takes a transaction-scoped advisory lock (`pg_advisory_xact_lock`) in addition to the docs/04 `FOR UPDATE`: `FOR UPDATE` cannot lock a row that does not exist yet, so two simultaneous FIRST reports could each create an incident. Proven by `test:db` (concurrent ingest → one incident). Throughput is irrelevant at our scale.
- [H3] db — no `char(n)` columns. Supabase Realtime truncates char(n) to 1 character (measured: 'K7Q2M' arrived as 'K'), which also made its per-subscriber RLS check drop every `incidents` event. Ids are `text` + CHECK `^[0-9A-HJKMNP-TV-Z]{5}$`. Migration 0001 was corrected in place (never deployed anywhere).
- [H3] db — unparsed reports have no client id: `client_id` is nullable with its own idempotency index (channel + md5(raw) + sender hash).
- [H3] db — `audit_events` immutable by trigger (UPDATE/DELETE refused even for `postgres`) + revoked privileges. TRUNCATE is used only by `/api/demo/reset`.
- [H4] db — `incidents.band_override` (migration 0002): a dispatcher's band override survives later re-assessments; every assessment still records the computed band.
- [H4] data — 12 synthetic "(illustrative)" hospitals in wilayas 9/16/31; CHU-A/EPH-B/CHU-C placed so haversine×1.4 gives 24/9/58 min and reproduce docs/05 §5.1 (closest ≠ best; `nearestEd` = EPH-B). `seed.sql` is generated from `data/hospitals.seed.json` (`pnpm db:seed-sql`), which validates the capability vocabulary and the "(illustrative)" suffix.
- [H4] ingest — outcomes: `created` · `merged` (different id within 300 m/10 min = independent report) · `updated` (same packet id again, any channel = same report; JSON + SMS of K7Q2M stay merged_count 1) · `duplicate` (exact re-delivery) · `unparsed` (stored raw, 200).
- [H4] ingest — JSON channel converts to the same `DzmsdPacket` (one scoring path). Not carried into scoring in v1: `multi_impact` (not in DZ-MSD v1). `medical` is never stored with the report (no medical table yet: dropped, not logged).
- [H4] ingest — per-SMS-sender limit 3/hour (docs/05 §7): excess is STORED raw with `parse_error = rate_limited`, shown to the dispatcher, creates no incident and gets no reply (no flood amplification). Never dropped.
- [H4] sms — gateway webhook verified as documented at docs.sms-gate.app/features/webhooks: `X-Signature` = hex HMAC-SHA256(raw body + `X-Timestamp`), ±5 min. Payload `{event, payload:{message, sender, receivedAt, …}}`; send = `POST http://<phone>:8080/message` Basic auth `{textMessage:{text}, phoneNumbers}`. UNCONFIRMED until recorded from a device in P5: exact `receivedAt` format and the send response body; parser also accepts `phoneNumber`/`text`. A forged signature gets 401 and is not stored (it is not a message from our gateway).
- [H4] sms — `SMSGATE_MODE=sim` in local `.env.local` until the gateway phone exists (the example URL 192.168.1.50 would make every ACK fail).
- [H5] sms — pre-alert SMS uses only BASIC GSM-7: the docs/04 template's `~` is an extension char (2 septets, mangled by some phones); "risque estime" wording. docs/04 §6 updated.
- [H5] routing — only OSRM/ORS results are cached (`eta_cache`, 3-decimal ≈100 m cell); haversine×1.4 is left to `rankHospitals()` which flags it ETA_ESTIMATED. API returns `etaProvider` per hospital + `etaNotes`.
- [H6] routing — on macOS port 5000 is the AirPlay Receiver (answers 403): run the OSRM container on another port (e.g. `OSRM_URL=http://localhost:5001`). Observed during the G1 curl run; the chain fell back correctly.
- [H5] lifecycle — forward-only chain + CANCELLED (reason ≥5 chars). Reasons also required for band override and for choosing a facility other than the server-computed top recommendation. MERGED is never set by PATCH.
- [H5] api — rate limits (in-memory, per process; the Vercel backup gets per-instance limits): JSON ingest 30/min per IP, webhook 120/min per IP, SMS sender 3/h, dispatcher API 120/min per user. Body cap 16 KB. Demo reset clears them.
- [H5] auth — dispatcher/hospital endpoints accept a Supabase session (Bearer or cookies) + `profiles.role`. Demo logins `dispatcher@sellekni.test`, `hospital-a@sellekni.test` (CHU-A), `hospital-b@sellekni.test` (EPH-B), password = `DEMO_USER_PASSWORD` in `.env.local` (`pnpm db:users`).
- [H5] env — one repo-root `.env.local`: `next.config.ts` loads it with `loadEnvConfig(…, forceReload=true)` (a plain second call is a silent no-op: @next/env caches). `pnpm env:local` fills empty keys only and prints key names only.

## P5 — native SMS + outbox chain (24h clock; time-box for the native module started at 24h-H2 = 20:00)
- [24h-H2] native SMS — `modules/sellekni-native` gains `getSimInfo()`, `sendSms(to, text, {id, subscriptionId})` and the `onSmsResult` event (sent / delivered / failed + code) over `SmsManager.sendTextMessage` with one sent and one delivered PendingIntent per message id (delivered is mutable + explicit so the status-report PDU arrives; TP-Status ≥ 0x40 = failed). `createForSubscriptionId` for dual-SIM. Multipart only for a contact's Arabic text (result on the last part); packets are ≤ 160 GSM-7 and never split.
- [24h-H2] permissions — `SEND_SMS` (runtime, `PermissionsAndroid`) and `READ_PHONE_STATE` (asked only when the person taps "Show the SIMs": without it we get the default SMS SIM, no carrier). Android words the latter "make and manage phone calls": the screen says the app never places a call. Sideload only (Play restricts SEND_SMS).
- [24h-H2] chain — one pure runner (`src/alert/runner.ts` + `chain.ts`) used by the app AND the tests: HTTPS (probe 2 s → full JSON 8 s → compact JSON 15 s = same v1 contract minus `medical`/`device`) → after the first failed HTTPS attempt, silent SMS packet to GW1 → GW2 when GW1 failed / had no result in 60 s / was sent but undelivered for 60 s → emergency contacts get a readable text 60 s after the first gateway SMS (at once if no gateway) → failed messages back off 10 s·2ⁿ (cap 5 min) → ACK stops everything → 30 min: give up and say "call 14". A rejected HTTPS post (bad key) still lets SMS carry the packet.
- [24h-H2] idempotence / kill — each message is persisted as `sending` BEFORE Android gets it; after a kill, no result in 60 s = failed, resent with a new message id (`ID.key.attempt`); a late sent/delivered report from an older attempt still counts, a late failure of an older attempt does not. Ingest is idempotent on the incident id. Tests: 10 chain tests incl.
